  • Single service bottleneck. All five controllers funnel through one bean — ClinicServiceImpl. It has no business logic, only delegates. Any change to a repository contract forces a touch to ClinicService, ClinicServiceImpl, and the caller. Three files for every two-layer change.
  • Triple repo stacks inflate the graph. Fifteen repository classes implement four interfaces. All three stacks compile into the WAR; only one activates at runtime via a Spring profile string. A mistyped profile silently falls back to the JPA stack, with no startup warning.
  • Dead-end candidates are mostly proxy-resolved, not truly dead. SpringData*Repository classes show no inbound import edges because Spring Data JPA generates runtime proxies — they are not called directly in source. PetTypeFormatter and PetValidator are wired via XML conversionService bean and @InitBinder, not imports. Neither is truly dead.
  • CallMonitoringAspect is a hidden dead-end under the default profile. The @Around pointcut targets @Repository-annotated classes. Spring Data JPA repositories carry no such annotation on their proxy. The aspect compiles and loads silently but produces zero JMX metrics when the spring-data-jpa profile is active.
  • Service extraction candidate: Vet domain. VetController → ClinicServiceImpl → VetRepository is a self-contained read-only flow with caching. It touches no other domain data and could be extracted to a standalone microservice with zero coupling changes required in the owner/pet/visit path.

  • pets and owners are multi-writer hotspots. Both tables are written by JDBC, JPA, and Spring Data JPA implementations. A schema migration (add column, rename, change type) must be applied and tested against all three stacks, tripling the regression surface.
  • visits has no writer in the JPA owner path. JpaOwnerRepositoryImpl reads visits eagerly as part of the owner graph but never writes them directly — writes flow only through JpaVisitRepositoryImpl. This split read/write path means a developer tracing a visit-save bug must cross two impl classes.
  • Only one cached store: vets. findPetTypes() (called on every pet form render) is not cached. The types table is effectively static reference data — a prime candidate for @Cacheable to eliminate a SELECT on every form load.
  • N+1 risk is confined to the JDBC vet path. JdbcVetRepositoryImpl issues one SELECT specialty_id FROM vet_specialties WHERE vet_id=? per vet in a loop. The JPA and Spring Data paths both use LEFT JOIN FETCH. If the active profile is jdbc with a growing vet list, this will be the first latency hot-spot.
  • JSP views are terminal sinks — no feedback loop. Views are pure output. Any field added to the domain model that needs to be editable requires touching the model, repository, service interface, service impl, controller, and JSP — six layers for one field. This is the steepest change-amplification pattern in the codebase.

  • Every write immediately triggers a full-graph read. The redirect → showOwner post-create pattern re-loads the owner with all their pets AND all visits. For an owner with 10 pets and 50 historical visits, this is 60+ rows fetched just to render the confirmation screen. No lazy-load boundary exists in the JDBC or JPA paths.
  • findPetTypes() is an uncached SELECT on every pet form render. Pet type is reference data that changes perhaps once per deployment. Without @Cacheable("petTypes"), every GET /owners/{id}/pets/new hits the types table. Adding one annotation and one Caffeine cache entry eliminates this entirely.
  • The JDBC findPetById path is the worst over-fetch. JdbcPetRepositoryImpl.findById calls ownerRepository.findById(ownerId) which calls loadPetsAndVisits(owner) — a LEFT OUTER JOIN across all of the owner's pets and visits — to then do a linear scan in memory for one pet by ID. Three tables, unbounded rows, just to resolve a foreign key.
  • No global exception handler on the critical path. If findOwnerById or findPetById throws ObjectRetrievalFailureException (JDBC) or NoResultException (JPA), the exception propagates to SimpleMappingExceptionResolver, which renders the raw message in exception.jsp. There is no retry, no 404 mapping, no user-friendly fallback.
  • The visit flow is the highest-complexity change target. Adding a field to Visit requires changes in: Visit.java, all four VisitRepository impls, ClinicService, ClinicServiceImpl, VisitController, and createOrUpdateVisitForm.jsp. Seven files for one domain field — the widest change fan-out in the system.
